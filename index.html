Capítulo 1

Aplicações cliente-servidor

A ideia base de tudo o resto: alguém pede, alguém responde.

O que é

Numa aplicação cliente-servidor há dois papéis. O cliente inicia sempre a comunicação com um pedido. O servidor fica à espera, processa o pedido e devolve uma resposta. Os dois têm de falar o mesmo protocolo (as regras da conversa) e normalmente estão em máquinas diferentes, ligados pela rede.

Mnemónica · quem fala primeiroO cliente é o freguês, o servidor é o empregado de mesa.
O empregado nunca vai à mesa pedir-te nada: só responde ao que pedes. Por isso, o servidor não faz pedidos ao cliente (pergunta real do Moodle).

Aplicação web vs aplicação desktop

Uma aplicação Web é um programa guardado num servidor remoto e entregue pela Internet através da interface de um navegador. Uma aplicação desktop (standalone) está instalada na máquina: código, dados locais e base de dados (integrada ou num servidor) correm sobre o sistema operativo local.

Na versão web de um CRM, o código fica dividido: uma parte corre no browser (cliente) e outra no servidor web, junto à base de dados. O que circula entre os dois são pedidos e respostas HTTP.

URL e navegação numa página web

O que acontece entre escreveres um endereço e veres a página.

Anatomia de um URL

scheme:[//[user:password@]host[:port]][path][?query][#anchor]

https://www.continente.pt/pt-pt/public/Pages/searchresults.aspx?k=arroz
└─┬─┘   └──────┬───────┘└──────────────┬──────────────────┘ └─┬─┘
esquema       host                    path                 query string
  • Esquemas: http, https, ftp, mailto, file, data, irc.
  • A query string (depois do ?) leva pares nome=valor separados por &.
  • A âncora (#...) aponta para uma parte da página.
  • Os URLs só podem usar caracteres ASCII. O URL encoding troca cada carácter inseguro por % seguido de 2 dígitos hexadecimais, e o espaço passa a %20 ou +. Exemplo: Malásia → Mal%C3%A1sia (UTF-8).
Mnemónica · ordem do URL«Eu Uso Senha Num Porto, Passo Pela Query, Até à Âncora»
Esquema · Utilizador:Senha@ · Nome do host · Porta · Path · ?Query · #Âncora.

Sequência pedido-resposta de uma página

1. Utilizadorescreve o URL, clica num link ou num favorito
→
2. Pedido HTTPo browser pede a página ao servidor
→
3. Servidorabre o ficheiro (estático) ou executa código (dinâmico)
→
4. Browsermostra o HTML recebido
5. Pedidos extraum por cada imagem, CSS e script (no exemplo dos slides foram 35), possivelmente a outros servidores
→
6. Mostravai mostrando cada elemento à medida que as respostas chegam
→
7. JavaScriptexecuta o código do cliente, que pode gerar ainda mais pedidos

Porque é que o browser faz pedidos extra? Porque o HTML só tem referências às imagens, CSS e scripts, não os próprios ficheiros. Cada referência obriga a um novo pedido. Conta assim: 1 HTML + 10 imagens + 2 CSS + 3 JS = 16 pedidos.

Estático vs dinâmico, visto pelo browser

Conteúdo estático: o servidor abre o ficheiro (por exemplo a-diocese.html) e devolve-o. Conteúdo dinâmico: o servidor executa o código associado ao recurso e o resultado é a resposta, que pode ser HTML, outro código ou até binário.

Mnemónica · o browser é «cego» à cozinhaAo cliente chega o prato, não a receita.
Seja comida de lata (estático) ou feita na hora (dinâmico), o browser recebe sempre uma resposta HTTP. Pergunta real: receber conteúdo dinâmico «é o mesmo que receber um conteúdo estático».
Capítulo 3

HTTP: terminologia e mensagens

HyperText Transfer Protocol: as palavras que o professor usa e a forma exata das mensagens.

Definições a saber de cor

  • HTTP é um protocolo da camada de aplicação que usa TCP (porta 80) como transporte. Segue o paradigma pedido-resposta.
  • Resposta do gabarito à pergunta «HTTP é:» → «um protocolo de comunicação usado por todos os agentes web num canal de comunicação». A opção «um protocolo de comunicação», sozinha, só dá meia cotação.
  • Agentes: cliente HTTP (por exemplo o browser), servidor HTTP (Apache, IIS, Kestrel) e, pelo meio, proxies.
  • Proxy: intermediário que é servidor para o cliente e cliente para o servidor. Serve para cache, balanceamento de carga, filtragem de conteúdos e segurança, e permite atravessar firewalls. Pode haver vários proxies em cadeia.
  • Gateway: intermediário que passa a mensagem a outro sistema (é daí que vem o «502 Bad Gateway»).
  • Ligação: o «circuito virtual» entre browser, proxies e servidor.

Stateless: sem estado

Cada troca HTTP é um pedido e uma resposta, e o servidor não se lembra de nada entre pedidos. Protocolos como FTP, SMTP e POP são stateful, porque mantêm uma sessão. No HTTP/1.1 a ligação pode manter-se aberta (persistent connection), mas isso serve só para eficiência e não guarda estado. Para haver estado é preciso construí-lo por cima, com cookies e sessões.

Mnemónica · statelessO HTTP tem memória de peixinho dourado.
Cada pedido é um desconhecido novo. Os cookies são o post-it que o cliente cola na testa para o servidor o reconhecer.

Armadilha (pergunta real): ao escrever https://www.ads.pt/ na barra, a linha gerada é GET / HTTP/1.1. Não é HTTPS/1.1, porque a versão é sempre «HTTP». Também não leva o domínio, que vai no cabeçalho Host, nem o URL completo.

A frase explicativa (OK, Not Found...) é para humanos: mudá-la não altera o comportamento de um cliente bem feito, que só olha para o código.

Métodos HTTP e GET vs POST

Os verbos do protocolo e a diferença que sai sempre em teste.

VersãoMétodos introduzidosPara quê
HTTP 0.9GETPedir um recurso (página, imagem...)
HTTP 1.0HEAD, POSTHEAD: só os cabeçalhos, sem corpo (para comparar versões). POST: enviar dados no corpo (formulários).
HTTP 1.1PUT, DELETE, OPTIONS, TRACE, CONNECT, PATCHPUT: guardar um recurso no servidor (upload). DELETE: apagar...
Mnemónica · versões0.9 → G. 1.0 → G + H + P («GHP, Grande Hotel do Porto»). 1.1 → o resto.

Os sites e aplicações web normais usam só GET e POST. As APIs REST usam os métodos como operações CRUD:

MétodoCRUDMnemónica

GETRead«Get = Ganhar, trazer cá»
PUTUpdate / Replace«Put: pôr no lugar, substituir tudo»
PATCHPartial update«Patch = remendo: só um bocado»
DELETEDelete«apagar»

GET vs POST

<form action="/pesquisa" method="get">  →  GET /pesquisa?q=UTAD HTTP/1.1      (dados no URL)
<form action="/pesquisa" method="post"> →  POST /pesquisa HTTP/1.1  ...  q=UTAD  (dados no corpo)
GETPOST
Onde vão os dadosNo URL (query string), à vista de todosNo corpo da mensagem
Voltar atrás / recarregarInofensivoReenvia os dados (o browser avisa)
Favoritos / cache / históricoSim / sim / ficam no históricoNão / não / não ficam
Tamanho / tipo de dadosLimitado (URL até cerca de 2048 caracteres), só ASCIISem limites, aceita binário

Mnemónica · GET vs POSTGET é um postal, POST é uma carta fechada.
O postal toda a gente lê (URL visível), cabe pouco (tamanho limitado), podes fotocopiar e guardar (favoritos, cache, histórico) e só leva texto (ASCII). A carta fechada leva o que quiseres lá dentro (corpo, binário, ficheiros), mas não a podes guardar nos favoritos.
Exame de 2021. Para uma pesquisa tipo Google, o melhor é GET: a pesquisa não altera dados e o URL com o resultado pode ser guardado e partilhado.
Capítulo 5

Cabeçalhos HTTP

Metadados em pares nome: valor, nos pedidos e nas respostas.

Os cabeçalhos deixam cliente e servidor passar informação adicional. Ficam depois da primeira linha e antes da linha vazia, e usam-se nos pedidos e nas respostas (pergunta real).

Os 4 grupos

GrupoO que fazExemplos
GeneralAplica-se a pedidos e respostas, sem descrever o corpoDate, Connection, Cache-Control, Warning
RequestInformação sobre o pedido ou sobre o clienteHost, User-Agent, Referer, Authorization, Accept-Encoding, If-Modified-Since
ResponseInformação sobre a resposta ou sobre o servidorLocation, Server, WWW-Authenticate
EntityDescreve o corpo (o conteúdo)Content-Type, Content-Length, Last-Modified, Content-Encoding
Mnemónica · grupos«Gatos Raramente Respondem Educadamente»
General · Request · Response · Entity. E a regra de ouro: se começa por Content-, fala do corpo, logo é Entity.

Os cabeçalhos que mais saem

HeaderTipoPara que serve
HostPedidoNome do servidor de destino. Permite o virtual hosting (vários sites num servidor). Obrigatório no HTTP/1.1.
User-AgentPedidoIdentifica o software cliente (browser). O servidor pode diferenciar a resposta por cliente.
RefererPedidoURL da página onde estava o link que originou o pedido. Não é enviado se o URL foi escrito à mão.
AuthorizationPedidoCredenciais, enviadas depois de um 401.
Accept-EncodingPedidoO cliente diz que aceita conteúdo comprimido e com que método (gzip, x-zip...).
If-Modified-SincePedidoPedido condicional: «manda só se mudou desde esta data», senão o servidor responde 304.
LocationRespostaNovo URL nos redirecionamentos 301/302.
WWW-AuthenticateRespostaAcompanha o 401 e diz o «realm» protegido.
ServerRespostaSoftware do servidor (por exemplo Microsoft-IIS ou Kestrel).
Content-TypeEntidadeTipo MIME do corpo. Aparece em respostas e também em pedidos com corpo (POST).
Content-LengthEntidadeTamanho do corpo em bytes. Obrigatório em pedidos com corpo (sem ele: 411).
Last-ModifiedEntidadeData da última alteração do conteúdo. Essencial para a cache.
DateGeralQuando a mensagem foi criada.
Referer (gabarito com 4 certas): indica o URL da página que estava a ser mostrada · o cliente indica o local que deu origem ao pedido · permite referenciar um recurso que não está no servidor de destino · permite distinguir um clique num link de um URL escrito na barra. Errada: «o servidor indica a referência base da resposta» (o Referer é um header de pedido, não de resposta). Nota: Referer está mal escrito de propósito na norma, só com um «r» antes do «er».
Accept-Encoding (gabarito com 2 certas): «indica que o cliente aceita conteúdos comprimidos» e «indica qual o método de compressão que pode ser usado na resposta». Não tem nada a ver com cifra nem com segurança.

Quem insere os cabeçalhos?

  • Pedidos: o browser e também o código da aplicação (por exemplo, JavaScript com request.setRequestHeader("Content-Type", ...)).
  • Respostas a conteúdo estático: o servidor web.
  • Respostas a conteúdo dinâmico: o servidor web e também o código da aplicação (Response.AddHeader("CustomHeader","CustomValue")).

Response buffering: o servidor retém a resposta até o script acabar (ou até Flush/End). É por isso que um AddHeader escrito a meio do HTML ainda funciona, já que os cabeçalhos ainda não saíram.

Forbidden header names

São cabeçalhos que o código não pode alterar, porque o browser controla-os: os que começam por Proxy- ou Sec-, e Accept-Charset, Accept-Encoding, Connection, Content-Length, Cookie, Date, Host, Origin, Keep-Alive, Referer...

Mnemónica · proibidosO browser não deixa mexer em «quem sou, por onde vou e o que aceito».
Quem sou: Host, Origin, Referer, Cookie. Por onde vou: Connection, Keep-Alive, Content-Length, Date. O que aceito: Accept-Charset, Accept-Encoding. Mais tudo o que começa por Proxy- e Sec-.
Capítulo 6

Tipos MIME

Multipurpose Internet Mail Extensions: a etiqueta que diz o que vem no corpo.

O MIME nasceu no e-mail e foi adotado pelo HTTP. O browser não confia na extensão do ficheiro: decide o que fazer com o corpo (mostrar HTML, desenhar uma imagem, chamar um helper...) pelo Content-Type.

Content-Type: tipo/subtipo [; parâmetros]

text/html        text/plain       text/css
image/gif        image/jpeg       audio/x-wav     video/mpeg-2
text/html; charset=utf-8          (o charset por omissão é ISO-8859-1)
Mnemónica · formato MIME«Família / Pessoa ; Detalhe»
image/gif = família image, membro gif. Depois do ; vêm os detalhes, como o charset. E o charset por omissão é ISO-8859-1: «o ISO é o Inicial».
image/gif (gabarito com 2 certas): «a mensagem tem no corpo os bytes de uma imagem» e «o cliente recebeu uma imagem».

Casos especiais

  • multipart: várias partes num corpo, separadas por uma fronteira (boundary): 
    Content-Type: multipart/x-mixed-replace; boundary=XPTOText
--XPTOText
Content-Type: image/gif
...
--XPTOText--          ← dois hífenes no fim = acabou
  • Base64 / data URI: incorpora o conteúdo no próprio HTML, sem pedido HTTP extra:
    <img src="data:image/gif;base64,R0lGODlh...">, com o formato data:[<mediatype>][;base64],<dados>.
  • A compressão negoceia-se à parte: o cliente envia Accept-Encoding e o servidor indica no Content-Encoding o que usou.
  • Pode ser alterado por código? Sim: numa resposta dinâmica a aplicação define o Content-Type (é assim que um controller devolve JSON ou um ficheiro PDF).
Capítulo 7

Códigos de estado

Três dígitos na linha de estado que classificam a resposta.

Porque existem? (Gabarito com 2 certas:) para classificar a resposta com um tipo e contexto e para os clientes interpretarem de forma fácil e rápida o tipo de resposta que recebem. Não são um checksum.

ClasseSignificadoMnemónica
1xxInformação: pedido recebido, a continuar«Aguenta aí»
2xxSucesso: recebido, entendido e aceite«Aqui tens»
3xxRedireção: é preciso mais uma ação«Vai ali»
4xxErro do cliente: pedido mal feito ou impossível«A culpa é tua»
5xxErro do servidor: falhou um pedido aparentemente válido«A culpa é minha»
Mnemónica · classes«Aguenta · Toma · Vai · Tu · Eu»
1 aguenta, 2 toma, 3 vai, 4 a culpa é tua, 5 a culpa é minha (servidor).

Os códigos a saber

CódigoNomeQuando e como lembrar
100Continue«Podes mandar o resto do corpo» (o cliente envia Expect: 100-continue).
200OKTudo certo, o recurso vem no corpo.
201CreatedFoi criado um recurso novo.
206Partial ContentVem só um pedaço (downloads em partes).
301Moved PermanentlyMudou-se para sempre, com Location. Proxies e browsers podem guardar em cache.
302FoundMudou-se temporariamente, com Location. É o que o RedirectToAction devolve.
303See Other«Vê noutro sítio, com GET» (depois de um POST).
304Not Modified«Usa a tua cópia em cache», em resposta a um If-Modified-Since. Vai sem corpo.
307 / 308Temporary / Permanent RedirectComo o 302 / 301, mas mantêm o método (um POST continua POST).
400Bad RequestPedido mal formulado (sintaxe errada).
401Unauthorized«Quem és tu?»: falta autenticação. Vai com WWW-Authenticate.
403Forbidden«Sei quem és, mas não entras.»
404Not Found«Não existe.»
411Length RequiredFalta o Content-Length.
500Internal Server ErrorO código do servidor rebentou.
502Bad GatewayO intermediário (proxy ou gateway) recebeu uma resposta inválida do servidor de cima (upstream).
503Service UnavailableServidor em baixo ou sobrecarregado.
505HTTP Version Not SupportedVersão do HTTP não suportada.
Mnemónicas · os pares que confundem301 vs 302: «1 = 1ª e única morada nova (permanente); 2 = 2ª casa, de férias (temporário).»
401 vs 403: «401: o porteiro pede-te o cartão. 403: viu o cartão e mesmo assim não entras.»
502: «Bad Gateway = o estafeta (proxy) foi buscar a encomenda e trouxe lixo.»
502 (gabarito com 2 certas): «o servidor proxy que representa o servidor de gateway não consegue obter um bom resultado do servidor de upstream» e «problemas de acesso provocados por uma falha na comunicação entre dois ou mais servidores que retransmitem dados entre si».
404, a maior armadilha: o gabarito do professor deu como certas «erro de processamento do pedido» e «erro por pedido mal formulado». Na norma, o 404 é Not Found e «mal formulado» é o 400. Se te aparecer esta pergunta com estas opções, responde como o gabarito.

Exemplos dos slides

http://www.utad.pt   →  307 → http://www.utad.pt/  → 200
http://www.utad.pt/pt/index.asp  →  302 Object Moved, Location: .../pt/index.html
ASP.NET:  HTTP/1.1 302 Found · Content-Length: 0 · Location: /MyController/MyRoute

Diretoria sem a barra final (livro): /~shklar é redirecionado (301) para /~shklar/. Sem a barra, os URLs relativos da página seriam resolvidos de forma errada.

Capítulo 8

Servidor web: resolução de endereços

Como o servidor descobre que ficheiro corresponde a /tc/index.html e se o podes ver.

O caminho de um pedido no servidor

Suporte de comunicações de rederecebe o pedido e envia a resposta
→
1. Resolução de endereçosVirtual hosting · Address mapping · Pseudónimos · Autenticação
→
2. Processamento do pedidoestático (static, as-is) ou dinâmico (CGI, SSI, APIs, Servlets...)
→
3. Geração da resposta
Mnemónica · as 3 etapasO servidor joga RPG: Resolve → Processa → Gera.

Definição do gabarito: a secção «Address Resolution» é «um conjunto de etapas que visam identificar os ficheiros responsáveis pela produção da resposta e verificar a permissão de acesso a estes».

Mnemónica · os 4 passos da resolução«Vê A Pasta Autorizada»
Virtual hosting (que site?) → Address mapping (que pasta e ficheiro?) → Pseudónimos (há atalhos?) → Autenticação (tens autorização?). A frase resume o que a resolução faz: encontrar a pasta e verificar se estás autorizado.

1. Virtual hosting

Um servidor (e até um único IP) aloja vários sites. Como sabe qual queres? Pelo cabeçalho Host. Sem o Host, GET /tc/index.html enviado para 188.114.97.5 seria ambíguo.

<VirtualHost *:80>
    ServerName   www.tribunalconstitucional.pt
    DocumentRoot /var/www
    <Directory /var/www>  DirectoryIndex index.php ... </Directory>
</VirtualHost>
Exame de 2021. Um servidor com várias aplicações, todas com wwwroot\images\logo.png, recebe GET /images/logo.png. Como decide qual usar? Pelo Host, que identifica o virtual host, e pela raiz (DocumentRoot) desse host.

2. Address mapping

Traduz o caminho do URL para um ficheiro no disco, a partir da raiz web (DocumentRoot). Não faz sentido a raiz do URL ser a raiz do disco, porque exporia o sistema todo.

ServidorRaiz web por omissão
Apache (Linux)/var/www
Apache (Windows)C:/Program Files/Apache Software Foundation/Apache2.2/htdocs/
IIS (Windows)c:\Inetpub\wwwroot
ASP.NET Corea pasta wwwroot do projeto

Exemplo: com DocumentRoot /var/www, /tc/index.html → /var/www/tc/index.html. O servidor verifica se a pasta tc existe e se tem lá o ficheiro index.html.

3. Pseudónimos (aliases)

Alias "/image" "/ftp/pub/image"          → /image/x.png vem de /ftp/pub/image/x.png
Alias /tc/ /var/tc/
Alias /tc/index.html /site/index.asp?id=tribunal

Ligam um caminho do URL a uma pasta fora da árvore do DocumentRoot. Assim, dão acesso a conteúdo que o virtual host normalmente não alcançaria e permitem partilhar ficheiros entre virtual hosts.

Pseudónimos (gabarito com 3 certas): mascarar caminhos para ficheiros · mudar os nomes aos ficheiros · associar recursos externos à estrutura de ficheiros da aplicação web. Erradas: criar endereços do servidor, esconder ficheiros, proteger de ataques.
Mnemónica · pseudónimoUm pseudónimo é um nome artístico.
O ficheiro tem o nome verdadeiro e a morada verdadeira no disco, mas o público conhece-o pelo nome artístico (o caminho no URL). Mascara o caminho, muda o nome e traz de fora conteúdo para a aplicação.

4. Autenticação

Servidor:  HTTP/1.1 401 Unauthorized
           WWW-Authenticate: Basic realm="User Visible Realm"
Cliente:   GET /tc/index.html HTTP/1.1
           Authorization: Basic QWxhZGRpbjpPcGVuU2VzYW1l    (user:pass em Base64)
Módulo de Autenticação (gabarito com 2 certas): «a componente que verifica se o pedido tem as permissões de acesso ao recurso solicitado» e «a secção responsável por gerar mensagens de resposta com o código 401». Erradas: «verifica username e password», «gera um formulário», «onde os utilizadores se autenticam».

No fim da resolução de endereços já se sabe o recurso (ficheiro) e a autenticação está verificada. Falta saber se o ficheiro é estático ou dinâmico, e isso é o capítulo seguinte.

Proxies e tipos de cache

Os intermediários entre o browser e o servidor, e os três sítios onde se guardam cópias das respostas.

O que é um proxy

Na prática, o browser e o servidor quase nunca falam diretamente: pelo meio há um ou mais proxies. O cliente faz o pedido ao proxy, o proxy faz o pedido ao servidor (ou ao proxy seguinte), recebe a resposta e devolve-a ao cliente.

Cliente HTTP(browser)
⇄
Proxyservidor para o cliente,
cliente para o servidor
⇄
Mais proxies…
⇄
Servidor HTTP(IIS, Apache…)

Definição dos slides: os proxies atuam como intermediários entre clientes e servidores e podem ter vários propósitos. O seu uso pode melhorar a segurança, o desempenho e a escalabilidade, e oferece serviços como cache, balanceamento de carga (load balancing) e filtragem de conteúdos. O livro acrescenta que permitem passar mensagens HTTP através de firewalls e suportar server farms (várias máquinas que parecem um só servidor por fora).

Mnemónica · o que faz um proxyO proxy é o porteiro do prédio: Segura, Copia, Balança e Filtra.
Segura a porta (segurança, atravessar firewalls) · guarda Cópias das encomendas (cache) · Balança as visitas pelos elevadores (balanceamento de carga, server farms) · Filtra quem entra (filtragem de conteúdos).
E tem duas caras: para o cliente parece um servidor, para o servidor parece um cliente.
Ligações com outras matérias: o 502 Bad Gateway é o proxy ou gateway a receber uma resposta inválida do servidor de cima (upstream). O 407 Proxy Authentication Required é o «401 dos proxies». Um proxy que guardou um 301 em cache pode continuar a redirecionar mesmo depois de o servidor mudar (o problema do login).

Cache web: definição

Cache web é o armazenamento temporário de páginas, imagens e outros ficheiros, para reduzir o uso da largura de banda e aumentar a velocidade de acesso. Em vez de repetir o pedido à fonte original, usa-se a cópia guardada.

Os três tipos de cache

TipoOnde ficaO que evitaNotas
Server-side (lado do servidor)No servidorEvita que o servidor gere a resposta outra vez do zero (HTML, imagens geradas dinamicamente…)Específica de cada aplicação, fora da norma HTTP. Exemplo: Output Caching no ASP.NET.
Client-side (lado do cliente, browser)No browser (memória ou disco)Evita que o cliente faça o pedido, ou que o servidor reenvie um recurso que não mudouControlada pelos cabeçalhos HTTP. Só serve um utilizador.
Proxy-side (nos proxies)No proxy, entre cliente e servidorEvita ir ao servidor de origem quando outro utilizador já pediu o mesmoÉ uma cache partilhada por muitos utilizadores. Não pode guardar respostas private.
Mnemónica · os três tipos de cacheTrês frigoríficos: o do restaurante, o de casa e o do supermercado do bairro.
Servidor = frigorífico do restaurante: guarda pratos já feitos para o cozinheiro não cozinhar outra vez.
Cliente = frigorífico de casa: se já lá tens, nem sais de casa (nem fazes o pedido).
Proxy = supermercado do bairro: é partilhado pelos vizinhos, por isso não guarda coisas privadas de ninguém.

Como funciona a cache no cliente (browser)

Segundo Shklar & Rosen, a cache do browser precisa de três componentes:

  • Módulo de geração de pedidos: antes de pedir, pergunta à cache se já existe uma cópia válida. Se a cópia expirou, acrescenta cabeçalhos de validação (If-Modified-Since).
  • Módulo de geração de respostas: lê os cabeçalhos da resposta para saber se pode guardar e por quanto tempo.
  • Módulo de cache: guarda os recursos e as datas de modificação (em memória ou no disco).
Exemplo dos slidesO que acontece
1. Client caches a responsePrimeiro pedido: 200 OK, e o browser guarda a resposta.
2. Client cache hitA cópia ainda é válida, por isso nem há pedido ao servidor.
3. Cached entry expiresA cópia passou o prazo (Expires ou max-age).
4. Revalidate hitPedido com If-Modified-Since. Não mudou, logo 304 Not Modified sem corpo, e usa-se a cópia.
5. Revalidate missMudou, logo 200 OK com o conteúdo novo, que substitui a cópia.
6. Proxy cache missO proxy não tem a cópia: vai ao servidor, guarda a resposta e entrega-a.
7. Proxy cache hitO proxy já tem a cópia (pedida antes, talvez por outro utilizador) e responde sem ir ao servidor.

Cabeçalhos que controlam a cache

Quem decide se uma resposta pode ir para a cache é o servidor ou a aplicação, porque são quem sabe se o conteúdo muda.

CabeçalhoPara que serve
Cache-Control: publicQualquer cache pode guardar, partilhada (proxy) ou local (browser).
Cache-Control: privateSó para um utilizador: o browser pode guardar, uma cache partilhada não.
Cache-Control: no-cacheSegundo o livro, nem browsers nem proxies podem guardar a resposta em cache. Na norma atual quer dizer «guardar, mas revalidar sempre antes de usar». No teste, segue o livro.
Cache-Control: max-age=NValidade em segundos.
ExpiresData a partir da qual a cópia expira.

O que pode ir para cache: os métodos cacheáveis são sobretudo GET e HEAD (o POST normalmente não; lembra-te do «GET vs POST: GET pode ser guardado em cache»). Os códigos cacheáveis por omissão incluem 200, 203, 204, 206, 300, 301, 404, 405, 410, 414 e 501.

Configuração no servidor: no Apache faz-se com mod_expires e mod_headers, por extensão (<FilesMatch "\.(gif|jpg|png|js|css)$"> Expires A2592000) ou por tipo MIME (ExpiresByType image/gif "access plus 1 month"). No ASP.NET Core usa-se [ResponseCache] e cache profiles para não repetir as definições em cada action.

O que acrescenta o livro (Shklar & Rosen, pp. 172–182)

  • Cache expirada não é apagada. Quando a entrada expira, fica guardada como «velha». No próximo pedido o browser revalida-a com If-Modified-Since. Se o servidor responde 304, reutiliza a cópia e renova-lhe a validade. Se responde 200, substitui-a pelo conteúdo novo. O livro diz que deitar fora a cópia expirada «may not be necessary».
  • HTTP/1.0 vs HTTP/1.1. No HTTP/1.0 o browser fazia um HEAD, comparava o Last-Modified e, se tivesse mudado, fazia um GET: podia precisar de duas trocas. No HTTP/1.1 basta uma, com If-Modified-Since.
  • Cache cheia. O browser remove as entradas expiradas e depois as menos usadas recentemente (LRU). Há cache em RAM e em disco, e as entradas podem passar da memória para o disco antes de serem apagadas. O tamanho máximo é configurável.
  • Chave da cache = o URL pedido, incluindo query string e conteúdo POST. Um Expires com uma data que já passou faz com que a entrada só dure a sessão.
  • Anomalia do histórico. O botão Voltar mostra muitas vezes a página guardada mesmo com Cache-Control: no-cache. O browser devia tratar o «Voltar» como um novo pedido.
Mnemónica · cache expiradaIogurte fora de prazo não desaparece do frigorífico.
Antes de o comeres, confirmas se ainda está bom (If-Modified-Since): se está, comes (304); se não, trocas por um novo (200). Só sai do frigorífico quando o trocas, quando o frigorífico fica cheio (LRU) ou quando o limpas. Atenção: um cookie expirado, pelo contrário, é destruído.
Capítulo 12 · Aula 06

Autenticação e cookies

As outras duas «interações HTTP complexas»: provar quem és e lembrar-se de ti.

Autenticação HTTP

A autenticação verifica a identidade do utilizador. A autorização verifica se ele tem acesso a um recurso. A autenticação HTTP é feita com cabeçalhos: o servidor pede as credenciais e o cliente envia-as.

1. Cliente:  GET /privado HTTP/1.1
2. Servidor: HTTP/1.1 401 Unauthorized
             WWW-Authenticate: Basic realm="User Visible Realm"     ← <type> realm=<área protegida>
3. Cliente:  GET /privado HTTP/1.1
             Authorization: Basic QWxhZGRpbjpPcGVuU2VzYW1l           ← utilizador:password em Base64
4. Servidor: HTTP/1.1 200 OK   (e o browser repete o Authorization nos pedidos seguintes do mesmo realm)
  • Esquemas: Basic, Bearer, Digest, HOBA, Mutual, Negotiate, OAuth, SCRAM e vapid.
  • O Basic só codifica em Base64, não cifra, por isso deve ir sobre HTTPS.
  • Quando é um proxy a pedir autenticação, a resposta é 407 Proxy Authentication Required.
Mnemónica · autenticação«Autenticação = quem és. Autorização = o que podes.»
O servidor responde 401 + WWW-Authenticate («identifica-te!»). O cliente responde com Authorization («aqui está o meu cartão»). O 407 é o mesmo, mas quem pede o cartão é o porteiro do meio (o proxy).

Cookies

São pares nome=valor que o servidor pede ao browser para guardar e devolver. São a forma de manter estado sobre um HTTP stateless (login, carrinho, preferências).

Resposta do servidor:  Set-Cookie: Name=Leon; Domain=.rutgers.edu; Path=/test/
Pedidos seguintes:     Cookie: Name=Leon      (só para *.rutgers.edu com caminho a começar por /test/)
TipoCaracterística
De sessãoSó em memória, sem data de expiração, apagado ao fechar o browser.
PersistenteGuardado no dispositivo, com data de expiração definida pelo servidor. Sobrevive ao fecho do browser.
First-partyCriado pelo domínio que estás a visitar (língua, analytics, preferências).
Third-partyCriado por outros domínios: rastreio entre sites, retargeting, publicidade (tracking cookies).

Estrutura: nome · valor · data de expiração (Expires ou Max-Age) · path · domain · Secure (só por ligação segura) · HttpOnly (só por HTTP, sem acesso por scripts).

Mnemónicas · cookiesSet-Cookie vs Cookie: «O servidor dá-te a senha do talho (Set-Cookie). Tu mostras a senha em cada visita (Cookie).»
Sessão vs persistente: «A senha do talho deita-se fora ao sair (sessão). O cartão de cliente tem validade e fica na carteira (persistente).»
First vs third-party: «O cartão da loja onde estás vs o espião da publicidade colado ao teu casaco.»
Estrutura: «Nunca Vi Elefantes Passar Depressa Sem Hesitar»: Nome, Valor, Expiração, Path, Domain, Secure, HttpOnly.

Variáveis de sessão (exame de 2021): os dados ficam no servidor e o cookie leva só o identificador da sessão. Sem cookies (cookieless), o identificador vai na query string ou como parte do URL.

Regras de domain e path (livro, 7.6)

  • domain=.mysite.com aplica-se a ecommerce.mysite.com e toys.ecommerce.mysite.com, mas não a mysite.com.
  • Um site só pode definir cookies para o seu próprio domínio: ecommerce.mysite.com pode usar .mysite.com, mas nunca .yahoo.com. Por isso os cookies de terceiros só entram através de recursos de apoio (imagens, CSS, JS, anúncios) servidos por outros domínios.
  • path=/ faz o cookie seguir em todos os pedidos ao servidor. path=/cgi-bin/ só nos URLs que começam por /cgi-bin/.
  • Os cookies criam uma sessão lógica, não uma sessão de rede.

Privacidade e P3P (livro, 7.7)

Os cookies de terceiros são considerados «particularmente perigosos» porque permitem seguir o utilizador entre sites. O P3P (Platform for Privacy Preferences, do W3C) permite ao site declarar a sua política de privacidade, legível por humanos e por máquinas, num <LINK>, num cabeçalho de resposta P3P ou em /w3c/p3p.xml. O browser compara-a com as preferências do utilizador e pode aceitar, bloquear, despromover (tornar não persistente) ou fazer leashing dos cookies (só os envia a terceiros quando o pedido vem de uma página do site original). Funciona «por honra»: o browser não consegue verificar se a política é cumprida.

Mnemónica · o que o P3P deixa o browser fazer«Aceita, Bloqueia, Despromove ou põe-lhe a Trela.»
Leash quer dizer trela: o cookie de terceiros só sai à rua acompanhado pelo site original.

Autorização: o que acrescenta o livro (7.8.2)

  • Os servidores protegem recursos por gamas de IP e por uma ACL (Access Control List, com utilizadores e passwords), organizada em realms.
  • Credenciais erradas levam a 401 outra vez. Ao fim de algumas tentativas, a maioria dos servidores passa a 403 Forbidden.
  • As credenciais aceites são reutilizadas para o mesmo realm.

Helpers e plugins (livro, 7.8.5)

Para formatos que não conhece, o browser tem 3 opções: suporte nativo, helper ou plugin. O helper apresenta o objeto fora da janela do browser (confuso para o utilizador) e só funciona com links diretos para o objeto. O plugin mostra-o dentro da página, através de <EMBED> ou <OBJECT> (o <EMBED> está obsoleto em favor de <OBJECT>). Se não houver associação para um tipo MIME, o browser usa um helper e deixa o sistema operativo escolher. É o módulo de interpretação de conteúdo que analisa o HTML e pede ao módulo de geração de pedidos os recursos de apoio.

Capítulo 13

Armadilhas do gabarito do professor

O que aprendemos com as perguntas reais do Moodle. Lê isto na véspera.

  1. Muitas perguntas têm várias respostas certas, mesmo com aspeto de escolha única. No Moodle, cada opção errada desconta. Assinala todas as que são verdade, e só essas.
  2. Prefere a opção mais completa. «HTTP é um protocolo de comunicação» deu meia cotação; a completa era «usado por todos os agentes web num canal de comunicação». O mesmo com o Plugin: «executado dentro do cliente web usado para renderizar conteúdos não conhecidos».
  3. «Nenhuma das opções» pode ser a certa (PHP/Java/Perl). Se todas as opções têm um erro («unicamente», «estáticos», «armazenamento», «pelos clientes»), escolhe-a.
  4. Palavras absolutas como «apenas», «unicamente» e «sempre» costumam tornar a opção falsa.
  5. O servidor nunca faz pedidos ao cliente.
  6. Para o cliente, dinâmico é igual a estático.
  7. 404: o gabarito aceitou «erro de processamento do pedido» e «pedido mal formulado».
  8. Códigos de estado servem para classificar a resposta com tipo e contexto, e para o cliente a interpretar depressa (2 certas).
  9. Linha de pedido: GET / HTTP/1.1, sem domínio e sem «HTTPS/1.1».
  10. Elementos que pedem sozinhos: <link>, <script> e <img>, sem o <a>.
  11. Aplicação web precisa de um servidor e um cliente.
  12. Header HTTP: usa-se nos pedidos e nas respostas.
